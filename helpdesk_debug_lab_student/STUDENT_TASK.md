# Практическая работа: диагностика и развитие Help Desk

## Часть 1. Развертывание

Самостоятельно:

1. Проверьте версии Java, Maven и Docker.
2. Разверните PostgreSQL командой `docker compose up -d db`.
3. Подключитесь к БД через pgAdmin/DBeaver/psql и найдите таблицы проекта.
4. Соберите Java-проект.
5. Запустите `Main`.
6. Запустите `Diagnostics`.
7. В отчёте приведите команды запуска и скриншоты/вывод успешного подключения.

## Часть 2. Анализ предметной области

Изучите таблицы и Java-классы. Составьте схему связей:

- Department → User;
- User → Ticket как автор;
- User → Ticket как исполнитель;
- Category → Ticket;
- Ticket → TicketComment;
- Ticket → TicketStatusHistory.

Для каждой связи укажите тип: 1:1, 1:N или N:M и объясните размещение внешнего ключа.

## Часть 3. Поиск и исправление дефектов

В проекте есть несколько независимых дефектов. Они находятся как в Java-коде, так и в SQL-схеме.

Требуется:

1. Воспроизвести каждый дефект.
2. Записать наблюдаемый симптом.
3. Найти первопричину.
4. Исправить её минимальным изменением.
5. Объяснить, почему исправление корректно.
6. Повторить диагностику.

Ориентируйтесь на проверки `Diagnostics`. Требуется добиться **11 PASS / 0 FAIL**.

### Ограничения

- нельзя удалять проверки из `Diagnostics`;
- нельзя подменять ожидаемые значения в диагностике;
- нельзя просто закомментировать проблемную функциональность;
- SQL должен оставаться параметризованным через `PreparedStatement`;
- нельзя заменить JDBC на Spring Data/Hibernate в базовой части;
- исправление должно сохранять архитектуру `Service -> Repository -> JDBC -> PostgreSQL`.

## Часть 4. Ручные сценарии проверки

После автоматической диагностики вручную проверьте:

1. Просмотр всех заявок.
2. Поиск заявки #1 по ID — тема и описание должны быть разными и корректными.
3. Фильтр `NEW`.
4. Поиск по фрагменту `Wi`.
5. Назначение заявки #1 Сергею (user id=2): остальные заявки не должны менять исполнителя.
6. Попытку назначить Анну (CUSTOMER, id=1) исполнителем — операция должна быть отклонена.
7. Комментарии заявки #1 — комментарии других заявок не должны отображаться.
8. Попытку перевести `NEW` напрямую в `RESOLVED` — должна быть отклонена.
9. Последовательность `NEW -> IN_PROGRESS -> RESOLVED -> CLOSED` — должна работать.
10. При ошибке записи истории статуса изменение статуса должно откатываться целиком.

## Часть 5. Краткий технический отчёт

Для каждого найденного дефекта заполните таблицу:

| № | Симптом | Как воспроизведён | Причина | Изменённые файлы | Как проверено |
|---|---|---|---|---|---|

В конце приложите итоговый вывод `Diagnostics`.

# Самостоятельная работа: улучшение функционала

После получения 11/11 PASS преподаватель назначает **один вариант**. Каждый вариант должен затронуть БД, модель Java, Repository, Service и интерфейс консольного приложения.

## Вариант A — SLA и просроченные заявки

Реализуйте контроль срока реакции/решения.

Требования:

- добавить в `tickets` поле `due_at`;
- при создании вычислять срок: `CRITICAL=1 ч`, `HIGH=4 ч`, `MEDIUM=8 ч`, `LOW=24 ч`;
- добавить метод Repository для получения просроченных заявок;
- `RESOLVED` и `CLOSED` не должны считаться просроченными;
- добавить команду меню «Просроченные заявки»;
- создать индекс, полезный для этого запроса;
- добавить минимум 3 диагностические проверки;
- объяснить, почему расчёт SLA находится в Service, а SQL-фильтрация — в Repository.

## Вариант B — теги заявок (Many-to-Many)

Добавьте теги `VPN`, `OFFICE`, `URGENT`, `REMOTE` и т.п.

Требования:

- таблица `tags`;
- связующая таблица `ticket_tags`;
- составной PK или эквивалентное ограничение уникальности;
- Java-сущность `Tag`;
- операции: создать тег, добавить к заявке, удалить, показать теги заявки;
- найти все заявки по тегу;
- не допускать повторного назначения одного тега одной заявке;
- добавить минимум 3 диагностические проверки.

## Вариант C — база знаний

Создайте сущность `KnowledgeBaseArticle`.

Поля минимум:

- `id`;
- `title`;
- `content`;
- `category_id`;
- `author_id`;
- `created_at`;
- `updated_at`.

Требования:

- CRUD статей;
- поиск по фрагменту заголовка;
- вывод статей той же категории при просмотре заявки;
- запрет пустого заголовка/содержимого;
- минимум один индекс для поиска/категории;
- минимум 3 диагностические проверки.

## Вариант D — загрузка сотрудников и история назначений

Требования:

- создать `ticket_assignment_history`;
- при каждом назначении фиксировать старого и нового исполнителя, автора изменения и время;
- операция назначения и запись истории должны быть одной транзакцией;
- вывести количество открытых заявок каждого SUPPORT;
- реализовать рекомендацию наименее загруженного сотрудника;
- ADMIN может назначать, CUSTOMER — нет;
- минимум 3 диагностические проверки.

## Бонусный уровень

Для любого варианта можно получить дополнительные баллы за одно из улучшений:

- optimistic locking (`version`);
- пагинация;
- полнотекстовый поиск PostgreSQL;
- Dockerfile для Java-приложения;
- миграции Flyway вместо init-скриптов;
- интеграционные тесты с Testcontainers.
